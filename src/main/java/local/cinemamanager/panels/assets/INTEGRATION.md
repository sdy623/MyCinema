# Private game-server picture assets

This feature lives only in the candidate10 checkout. It does not operate an HTTP server and does not upload to any external hosting provider. It adds a single game protocol on the existing authenticated player connection.

## Hooks owned by the integrating code

1. In the existing payload registration, call `AssetNetwork.register(registrar)` using the same versioned registrar as the panel messages.
2. In the mod constructor, register `AssetLimits.SPEC` as `ModConfig.Type.SERVER`. Defaults are 64 MiB/image and 512 MiB/world, with configurable maximum image size 256 MiB. Every source axis must be at most 8192; there is no aspect-ratio restriction.
3. Before URI normalization in `PosterPolicy.normalize`, recognize `AssetReference.normalize(value)`. The exact public syntax is `mycinema-asset:` followed by 64 lowercase hex SHA-256 characters. Asset references must never enter HTTP/file URI handling, redirect authorization, or `CinemaPermissions` URL policy.
4. The existing owner save path still calls `InfoTile.authorize` for the clicked panel, exact group signature and all member owners. For an asset source, use `PanelAssets.mayUseAsset(actor, tile, source)` instead of the URL-only policy. This helper requires the real connected actor to be a recorded uploader in this world and to have edit authority on the member. It deliberately does not impose an additional eight-metre limit on every member of a large group; the clicked target and transfer steps enforce that range.
5. An asset `PosterGrant.issue` must validate `PanelAssets.mayUseAsset(actor, member, source)`, then issue the ordinary private grant bound to the member identity and current owner. `PosterGrant.current` must retain all existing exact loaded-instance, identity, owner and source checks, then return `PanelAssets.current(tile, author, source)` for an asset. Assets are not universally publishable; `PosterPolicy.mayPublish(asset)` must return false so legacy/copy-forged NBT cannot skip grants. `PanelAssets.exists(tile, source)` is available for diagnostics. No server path or manifest is serialized into block NBT or guest metadata.
6. In `PosterImages.source`, recognize an asset reference before `MediaSource.normalize` and create an ordinary source using its opaque URI. In `PosterImages.read`, before the HTTP branch, route `mycinema-asset` to `PanelAssetClient.read(entry.context, budget, () -> entry.cancelled)`. Return those verified bytes into the existing full decoder and memory/texture budget path. No second decoder or texture cache is introduced.
7. The editor uses `PanelAssetClient.prepare(Path)` after a real local file selection. This returns a future of `Selection`, with only `filename()` and `bytes()` exposed for confirmation. Completion occurs on a file worker; marshal UI work back through `Minecraft.execute`. Show an explicit confirmation naming that file, its size, and upload to this game server. Only after confirmation call `PanelAssetClient.upload(new Context(clientLevel,pos,identity,serverSignature), selection, true, progressConsumer)` on the client thread. `Progress(state, transferred, total)` and completion callback run on the client thread. A successful result is the server-validated opaque reference, which can populate the poster field; the normal panel save still creates the owner grant. Cancel via `cancelUpload()` when the user cancels, editor closes, or its identity/signature changes. Error exceptions use stable `asset_*` codes; local paths do not leave this helper.
8. `PanelAssetClient` and `PanelAssets` subscribe to their own game tick/logout/server-stop events. Call `PanelAssetClient.clear()` from poster resource-reload clearing as well if it should cancel pending asset reads immediately. The client also independently checks the actual level connection every tick.

## Storage, ownership and lifecycle

Each save root has `mycinema-panel-assets-v1` with its own generated world identity. Final picture bytes use SHA-256 names and are immutable. A fixed ceiling of 4096 stored objects also bounds manifest memory independently of compressed byte quota. Private binary metadata stores world identity, dimensions, size and up to 256 uploader UUIDs. Only actual uploaders can author a new use of that hash; copying another player's public hash is insufficient. A new owner can select and upload the same picture normally, which proves possession and adds their UUID while deduplicating the immutable image. Existing public viewers may only download a hash currently approved on an exact loaded panel within 64 metres.

New uploads reserve the complete declared byte length against the world quota before writing. Existing same-hash/same-length uploads stream into a digest-only sink and must match the server-computed SHA-256; they can deduplicate at full quota without creating additional staging data. Client hash and length are always verified. Normal staged files are UUID-named and never derived from a client path. Recovery deletes only this feature's exact UUID `.part` names within its marked private directory. It preserves all finalized images and unrelated files.

Uploads are limited to four server-wide and one per actor; downloads to eight server-wide and one per actor. Packets contain at most 32 KiB. Uploads use acknowledgements and at most two accepted chunk packets per actor per tick. The server sends at most one download chunk per active viewer per tick and waits for its sequence acknowledgement before continuing. Requests are rate limited; replay nonces are bounded and never recycled within a connection. Server-generated UUID tokens bind all continuations to the original transfer. Idle timeout is ten server seconds, and the overall transfer window is fifteen minutes, which accommodates a 256 MiB image at the bounded rate.

A captured target lease checks real live connection, the original loaded tile object, its identity, owner, current group signature, dimension, interaction permission and distance at each server step and just before committing asynchronous validation. Uploads also recheck owner/editor permission across current group members. Downloads also recheck the current approved public source. No chunk is force loaded. Death, logout, changed ownership, new group revisions, panel replacement, disconnect, cancellation and server stop invalidate pending work. Client contexts additionally discard stale callbacks and verify byte count and final SHA-256 before decode.

The server validator streams PNG/APNG CRC/container data, JPEG marker/scan structure and WebP RIFF/frame structure through fixed-size buffers; it never allocates a source-sized raster. This is a structural validation boundary, not a claim that every compressed pixel stream is decodable. The client's existing full decoder is the final content check and retains all poster memory protections.

## Checks to run when a resource slot is available

- `AssetStoreChecks`: pure-Java disk/quota/manifest/dedup/restart/isolation and real PNG/JPEG/WebP structural fixtures.
- `AssetNetworkChecks`: actual Netty codecs, 32 KiB round trips, negative/oversized/truncated lengths rejected before allocation.
- `AssetPermissionGameTests`: opt-in loaded-world simulated actors for owner, identity, signature, distance, publication and block replacement checks. The production network deliberately rejects FakePlayer actors and never enables a test-authority flag.
- A real client/server upload, editor confirmation, cancellation, reconnect and another viewer render remain necessary integration acceptance checks.

All new error/status codes originate in these files. Translate them in the owner UI; do not display local exception causes or filesystem paths.
